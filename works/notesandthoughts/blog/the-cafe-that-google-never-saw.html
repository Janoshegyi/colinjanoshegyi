A note about the case

The investigation described here is real. For security purposes, I have changed the name of the affected café to Riverside Prague Cafe. The name is used only as an example and does not identify the actual website examined.

I reached out to the owner of the affected domain after finding the issue, although I did not receive a response. When I later checked the domain again using Cloaker Checker, the difference was no longer detected. I cannot say exactly when or how it was removed, but I am glad the site no longer appeared to be serving the malicious content.

I initially thought this was going to be a fairly ordinary hacked website. The more I compared the responses, the stranger it became.

The first thing that caught my attention was that the website looked completely normal in Chrome. Nothing obviously broken. No strange redirects. No gambling ads. Nothing.

Googlebot was getting a completely different website.

This report walks through how I found that difference, what cloaking is, how a server can decide who's really asking, and how you can safely check your own website.

What this is, and isn'tThis isn't an investigation into who carried out the attack. It's an investigation into how the attack was detected. The goal is to help website owners recognize the warning signs on their own websites, not to identify or accuse any particular individual or organization.

Log 01 · Foundations

What happens when you visit a website?

Before cloaking makes sense, it helps to see the plumbing underneath an ordinary page load.

DNS (Domain Name System) is the internet's address book, it translates a domain name into the address responsible for handling it. It tells the browser where to send the request; it doesn't normally decide what the page contains.

Sample HTTP request
GET / HTTP/2 Host: riverside-prague-cafe.example User-Agent: Mozilla/5.0 ... Chrome/... Accept: text/html Accept-Language: en-US,en;q=0.9

The request tells the server which page is wanted, what content types the browser accepts, which language is preferred, and, critically, what software claims to be making the request.

Sample HTTP response
HTTP/2 200 OK Content-Type: text/html <!DOCTYPE html> <html><head><title>Example website</title></head> <body>...</body></html>
Log 02 · The Identifying Header

What is a User-Agent?

The most important detail in this whole investigation is the User-Agent, a request header that tells the server what software claims to be visiting.

A normal Chrome browser sends something like Mozilla/5.0 (...) Chrome/.... Google's crawler identifies itself with a string containing Googlebot/2.1.

When Chrome DevTools is set to spoof the Googlebot User-Agent, the browser is simply saying "treat me as Googlebot". It does not become a real Google crawler. That distinction matters: a more careful cloaking system would also verify the visitor's IP address actually belongs to Google. Here, changing the header string alone was enough to trigger the alternate page, which points to a fairly simple check running somewhere in the delivery chain:

Illustrative logic (not recovered source)
const userAgent = request.headers.get("User-Agent") || ""; if (userAgent.includes("Googlebot")) { return alternatePage; } return cafePage;
Log 03 · Definition

What Is User-Agent Cloaking?

I find cloaking interesting because it attacks one of the assumptions we normally make about the web: that a URL represents a page. It doesn't necessarily. A URL can represent different things to different visitors, and sometimes the difference is deliberate.

Cloaking means serving substantially different content depending on who the server believes is visiting. Not every difference is malicious. A mobile layout, a translated page, or an authorized A/B test can all be legitimate. The important question is whether the essential subject stays the same.

A mobile café page and a desktop café page are still about the café. A Czech café page and an unrelated spam page are not the same subject wearing different clothes. They're two unrelated websites sharing one address.

Log 04 · Motive

Why Search-Engine Cloaking Is Valuable to SEO Spam Campaigns

In this kind of compromised-site case, the goal is usually SEO spam. SEO spam operators benefit from things a brand-new domain doesn't have: age, real backlinks, a history in Google's index, an existing reputation, and regular crawler visits. Rather than building that authority from zero, this scheme borrowed the café's. The same pattern shows up just as often behind a pharmacy spam campaign, a crypto scam, or a page of counterfeit product listings. Whatever content the destination site is selling, it needs search visibility it hasn't earned on its own. In this case, the alternate content happened to promote online gambling.

The strategy in one lineOrdinary visitor sees the real café, so the owner notices nothing. The search crawler sees the alternate content, so the search engine indexes those keywords under a trusted domain.

That asymmetry, invisible to humans, visible to crawlers, is the entire reason cloaking can run undiscovered for a long time.

Where does parasite SEO fit in? Parasite SEO is a broader search-spam strategy built around exploiting the authority, trust, or existing visibility of another website or platform to rank content that would struggle to rank on its own. In a compromised-site campaign, user-agent cloaking can act as the delivery mechanism: normal visitors receive the legitimate site while search-engine crawlers receive the SEO spam. The two concepts overlap, but they describe different parts of the operation.

Log 07 · Where The Swap Happens

Why the raw HTML response matters

A page can be altered in two very different places, and the distinction changes the entire investigation:

Client-side: normal HTML arrives → JavaScript runs in the browser → the visible page changes afterward Server-side / edge-side: request arrives → visitor is classified → the HTML itself is chosen before anything is sent

In this case, the alternate markup was already present in Network → Document → Copy response, meaning the browser never built the café page and then swapped it. The malicious document was sent across the wire as the very first response. That rules out a browser extension or a simple CSS trick, and points at the origin server, a reverse proxy, a CDN edge function, or a compromised hosting integration.

Log 08 · Payload Anatomy

The SEO Machinery Hidden Inside a Cloaked Response

The cloaked page wasn't a crude spam banner, it was engineered with the same care a legitimate SEO team would use.

Title & meta description

The title becomes the clickable headline in search results; the description often becomes the preview text beneath it. Both were rewritten to promote the alternate content.

Robots directive

<meta name="robots" content="index, follow, nosnippet">

index invites the page into Google's index. follow invites crawlers to follow its links. nosnippet asks Google not to show a normal text preview, The configuration allows the page to be indexed while suppressing a normal text snippet. Taken together with the gambling content and hidden links, the setup is consistent with an SEO-spam campaign.

Canonical URL

<link rel="canonical" href="https://riverside-prague-cafe.example/" />

A canonical tag tells search engines which URL is the preferred version of a document. It is not a redirect. It is a hint. Here, the alternate document declared the café homepage as its canonical URL, attempting to associate the alternate content with that URL.

Hreflang, AMP, Open Graph

Several alternate-language and AMP references point to a suspicious subdomain. Open Graph and Twitter card tags were also present, which can control how a page appears when shared or previewed.

JSON-LD structured data

Structured data gives search engines machine-readable claims instead of making them infer everything visually. This page claimed to be a product, a brand, an organization, and an FAQ resource, complete with a fabricated 4.9 rating and named customer reviews. Search engines don't have to believe any of it, and misleading structured data can be ignored or penalized, but it's cheap to add and occasionally works.

Log 09 · The Backlink Network

Hidden Links, SEO Spam, and the Parasite SEO Connection

Buried in the page was a block styled display:none, invisible to a visitor, but still present in the HTML and still readable by a crawler:

<div style="display: none;"> <a href="[redacted-domain]">example gambling anchor text</a> <a href="[redacted-domain]">another example gambling anchor text</a> </div>

The visible words inside a link are its anchor text. Repeating spam-flavored anchor text across many hidden links is an attempt to associate the destination domain with those exact search phrases. One compromised café rarely moves the needle alone, the technique only works at scale, across many unrelated compromised sites feeding the same destination:

Modern search engines catch and discount plenty of hidden-link schemes, but only a fraction of the links need to survive, and only temporarily. At larger scale, the same technique can be repeated across many unrelated compromised domains.

Log 10 · Template Origin

Why is there so much Shopify and Apple code?

The alternate page referenced example-store.myshopify.com and example-retailer.example, and even carried a leftover product path for an iPhone listing. That reveals the likely build process:

  1. Copy an existing Shopify product page from another storefront
  2. Mirror its HTML, CSS, and JavaScript wholesale
  3. Swap the headings, images, and product data for the alternate content
  4. Keep the rest of the structure, Shop Pay code, trade-in terms, store-locator widgets, untouched
  5. Serve the result from the compromised café domain

Those Shopify and Cloudflare scripts appear to be inherited template components. Their presence alone doesn't tell us where the compromise lives. They're inherited scaffolding from the page that got cloned. This is worth noting so an investigation doesn't waste time chasing the wrong script.

Log 11 · Why It Works

The mechanics of staying invisible

  • The owner sees the normal website. Nothing looks broken when they check.
  • Customers see the normal website too. Direct visitors rarely trigger the alternate path, so complaints stay quiet.
  • Basic uptime monitors can miss it. Most only check for a 200 response, which this always returns.
  • Crawlers get everything upfront. The alternate title, description, structured data, and links arrive in the very first response, no JavaScript required.
  • Trust is borrowed, not built. An established local domain gets crawled and trusted faster than a brand-new spam domain ever could.
Log 12 · Reproducing The Test

How to Detect User-Agent Cloaking on Your Website

  1. Open DevTools. Press F12 or Ctrl+Shift+I, then select the Network tab.
  2. Start clean. Enable "Disable cache," click "Clear network log."
  3. Record the normal version. Hard-reload with Ctrl+Shift+R, select the Doc filter, click the main document request, right-click → Copy → Copy response, save as normal-homepage.html.
  4. Spoof the User-Agent. Open the DevTools menu → More tools → Network conditions → uncheck "Use browser default" → choose Googlebot.
  5. Record the Googlebot User-Agent version. Clear the log again, reload, confirm the request header now shows Googlebot/2.1, then copy the response as googlebot-homepage.html.
  6. Diff the two files. Search both for <title>, meta name="description", canonical, robots, application/ld+json, display: none, and any unfamiliar outbound domains.

A meaningful difference in topic, language, or destination links between the two files is a strong warning sign. If you want to automate the comparison, Cloaker Checker can scan your website for user-agent cloaking.

Log 13 · Standard Of Evidence

What makes the strongest case

Not a screenshot of the visible page, the combination of the same URL, different User-Agent headers, two materially different raw responses, and alternate content that was already present before anything rendered. A solid evidence package includes a normal-browser HAR, a Googlebot HAR, both raw HTML files, header screenshots, timestamps, DNS records, and any CDN worker or rule configuration you can access.

A note on HAR filesHTTP Archive exports can contain sensitive information, cookies, tokens, session data. Sanitize before sharing.

Proving the malicious page exists is not the same as proving where the compromise lives.

Log 15 · Response Playbook

If this happens to a site you own

Preserve evidence first

Save HAR files, raw HTML, screenshots, logs, DNS records, and worker configurations with timestamps before changing anything.

Walk the delivery chain

DNS → CDN / edge worker → reverse proxy → hosting platform → application → files & database

Check each layer in order, Cloudflare Workers, Snippets, redirect and transform rules, origin rules, DNS records, and account audit logs are the most common hiding spots.

Audit the server itself

Recently modified files, .htaccess, Nginx config, unknown admin accounts, deployment history, and unfamiliar plugins or integrations.

Rotate everything

Hosting passwords, CDN passwords, API tokens, FTP/SFTP credentials, CMS admin accounts, email passwords, deployment keys, and turn on multi-factor authentication everywhere.

Remove the routing logic, not just the page

Deleting the alternate HTML alone won't help if a worker or server rule is generating it dynamically, it will simply return.

Clean up with search engines

Verify through Search Console, inspect affected URLs, check for manual actions, request recrawling once fixed, and file for reconsideration if needed.

The one-sentence lesson

A website can look completely normal to its owner while serving something else entirely to search engines, a visual check from a browser is not an audit.

Security and SEO reviews should periodically compare responses across a normal browser, Googlebot, Bingbot, different referrers, and different countries, and monitor more than uptime: titles, content hashes, response sizes, languages, new canonical tags, and any crawler-specific branching in the response.

The internet doesn't always serve everyone the same truth. Sometimes the only way to understand what a website really is, is to ask it from someone else's perspective.

FAQ · QUICK ANSWERS

Cloaking, Parasite SEO, and SEO Security FAQ

What is user-agent cloaking?

User-agent cloaking is when a website serves different content depending on the User-Agent making the request. In SEO abuse, a compromised site can show normal content to visitors while serving spam or manipulated content to Googlebot and other crawlers.

What is parasite SEO?

Parasite SEO is a strategy that uses the authority, trust, backlinks, or existing visibility of another website or platform to help content rank. On a compromised website, cloaking can be used to hide that content from ordinary visitors.

How can I detect SEO cloaking?

Compare the response returned to a normal browser with the response returned to a crawler User-Agent. Differences in titles, meta descriptions, canonicals, robots directives, structured data, language, content, or outbound links can indicate cloaking.

Why is cloaking also a web security problem?

Cloaking can be a symptom of a compromised website, application, server rule, CDN rule, reverse proxy, or account. A normal visual check may miss the problem because the malicious response is selectively delivered to crawlers.

What is the difference between SEO cloaking and parasite SEO?

Cloaking describes how different content is delivered to different requesters. Parasite SEO describes the broader strategy of exploiting an established site's authority or visibility to help unwanted content rank.
